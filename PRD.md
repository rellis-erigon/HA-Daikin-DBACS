# Daikin D-BACS for Home Assistant — PRD

**Status:** reviewed, decisions recorded · **Revised:** 2026-10-13 · **Target HA:** 2026.10 or later

A Home Assistant custom integration that talks BACnet/IP to a Daikin
"Interface for use in BACnet" gateway, turns each indoor-unit group into a
Home Assistant device, and draws them with the
[HA-Cards](https://github.com/rellis-erigon/HA-Cards) `hvac-controller-card`.

---

## 0. Decisions taken

Recorded here so the phases below are read as settled scope rather than
options.

| # | Decision |
|--:|---|
| 1 | **Target is the DIII-NET gateway** (`DMS502B51` / `DMS502B71`), not an intelligent Touch Manager. The iTM (`DCM014A51`) is a possible later addition and a **different object model** — out of scope for this document. |
| 2 | **Phase 1 is read-only.** No `WriteProperty` of any kind ships in the first release. |
| 3 | **Outdoor units** become synthetic devices rolled up from the indoor groups that share a refrigerant system, in Phase 4, with the mapping entered by hand. |
| 4 | **Assume a BMS head-end is already connected** to the gateway. It is not ours, we do not disturb it, and the write path must be designed around it. |
| 5 | **Design for the full 256 groups.** Discovery detects unpopulated and dead groups and ignores them rather than assuming a small system. |
| 6 | **Selective COV plus a slow poll.** COV on four points per group; everything else polled on a long interval. |
| 7 | **Alarms are read passively.** We never register as a BACnet event notification recipient. |
| 8 | **Read-only probing of a live gateway is permitted** during development. Writes only in an agreed window. |

## 1. Research — what already exists

### 1.1 The gateway

"D-BACS" is Daikin's **D**aikin **B**uilding **A**ir-**C**onditioning
**S**ystem — the family name, not a model. The box that speaks BACnet/IP in
it is the **Interface for use in BACnet**, model `DMS502B51` / `DMS502B71`
(also sold as `DAM502B51`), optionally carrying up to three extra DIII
boards (`DAM411B51`). On the air-conditioning side it speaks **DIII-NET**
(D3) to the indoor units; on the network side it is a plain BACnet/IP
device.

Capacity, which matches the supplied point list exactly:

| | |
|---|---|
| DIII-NET ports | up to 4 |
| Groups per port | 64 (addresses `1-00` … `4-15`) |
| Indoor-unit groups total | **256** |
| Indoor units | up to 512 (2 per group) |
| Outdoor units | up to 40 |

### 1.2 The supplied point list — verified

The supplied `BACnet_Object_List.pdf` was decoded and every claim in it
checked against Daikin's own
[BACnet/IP Functional Specifications, Version 6 (CB07A004G)](https://tinlavir.ro/parteneri/2_VRV/4_Control_Systems/06_BACnet_Gateway/Documents/Databooks/DMS502B51-71_FunctionalSpecifications1_ver6.34.00(CB07A004G)_tcm135-86223%20(1).pdf).
**It verifies**, with three corrections and one significant omission.

**Instance numbering.** The supplied list gives 256 rows of instance numbers.
It does not need to — they are computed. Daikin packs the instance number as:

```
bit  31────22 21────16 15──────8 7──────0
     obj type  unused   AC number  member
```

so, for the instance portion:

```
instance = (AC number × 256) + member number
```

The AC number is the position in DIII address order:

```
AC number = 64 × (port − 1) + 16 × (line − 1) + group        # port 1-4, line 1-4, group 0-15
port  = AC // 64 + 1      line = (AC % 64) // 16 + 1      group = AC % 16
```

Spot checks against the supplied list: port 1 `1-00` member 1 → AC 0 →
instance 1 ✓ · port 1 `2-00` → AC 16 → 4097 ✓ · port 2 `1-00` → AC 64 →
16385 ✓ · port 4 `4-15` → AC 255 → 65281 ✓. **All 256 rows are generated by
that formula, so the integration computes instances and never ships a
table** — and the same formula generates a complete synthetic fixture for
tests.

**Corrections to the supplied list:**

1. Member 19 (Accumulated Power) is shown with no object name or type. It is
   an **Accumulator** object (BACnet type 23), and the spec notes it is
   "supported by certain models only".
2. The list stops at member 31. The spec adds **members 32–35** (Ventilation
   Mode and Ventilation Amount, setting and status) for Heat Reclaim
   Ventilators, in edition G.
3. Members 15 and 18 are marked Vacant. Member 18 exists but is
   **Japanese market only**.

**The omission that matters:** there are **no outdoor-unit objects**. The
gateway's object model is indoor-unit groups and HRVs, full stop. The only
outdoor information published is `CompressorStatus_XXX` — "the compressor of
the outdoor unit connected to *this indoor unit* is running" — and an
outdoor fault surfaces as a malfunction code on the indoor units in that
refrigerant system. Decision 3 above is the response.

**Enumerations** (these are not guessable, and getting them wrong silently
mislabels every unit):

| Point | Type | Values |
|---|---|---|
| `AirConModeCommand` | MO | 1 Cool · 2 Heat · 3 Ventilate · 4 Auto · 5 Dry |
| `AirConModeStatus` | MI | 1 Cool · 2 Heat · 3 Fan · 4 *(not used)* · 5 Dry |
| `AirFlowRateCommand/Status` | MO/MI | 1 **Low** · 2 **High** · 3 **Middle** · 4 Auto |
| `AirDirectionCommand/Status` | AV/AI | 0–3 Horizontal · 4 Vertical · 7 Swing |
| `TempAdjust` | AV | °C or °F, `Relinquish_Default` 25 °C / 75 °F. VRV range ≈ 20–35 cool, 15–30 heat, **varies by unit model**; out-of-range writes are silently clamped by the unit |
| `MalfunctionCode` | MI | 1 Normal, >1 manufacturer-specific; the two-character Daikin code (`U1`, `E7`…) is in the object's **Description** property, not its value |
| `Alarm` | BI | Normal / Malfunction |

Note the airflow ordering — **Low, High, Middle, Auto**. Not a typo on
Daikin's part, and a trap for anyone who assumes 1-2-3 is low-medium-high.

**Protocol facts** worth designing against:

- `Max_APDU_Length_Accepted` = **1024**, `Segmentation_Supported` =
  SEGMENTED_BOTH, `Max_Segments` = 100.
- `ReadPropertyMultiple`, `WriteProperty` and `WritePropertyMultiple` all
  supported. `Priority_Array` and `Relinquish_Default` are **readable**, so
  we can see what another client holds before writing anything.
- `SubscribeCOV` is **executed by the gateway** (BIBB DS-COV-B), on every
  object **except accumulated power**. `COV_Increment` on the temperature
  objects is fixed at 1.0 °.
- **COV recipients: 5 per object.** Per object, not per gateway — so an
  existing head-end's subscriptions do not lock us out. A sixth returns
  `COV_SUBSCRIPTION_FAILED (43)`.
- **COV subscriptions are not retained across a power cycle.** The gateway
  forgets them silently, so a reboot must be detected and the subscriptions
  rebuilt.
- `Active_COV_Subscriptions` is readable (firmware 6.20+) — we can see what
  else is subscribed before adding ourselves.
- **Event notification recipients: 10 in total**, gateway-wide, registered by
  writing the Notification Class object's `Recipient_List`. A different and
  much scarcer resource than COV. Decision 7 keeps us out of it.
- Error responses we rely on: `UNKNOWN_OBJECT (31)` for an object that is not
  implemented — i.e. **a group that is not populated** — and
  `DEVICE / CONFIGURATION_IN_PROGRESS (2)` while the gateway is still
  scanning the D3 network. The difference between "not there" and "not ready
  yet" is what makes dead-group detection trustworthy.

And one hard constraint, quoted from the spec: *"the number of changes for
each setting should not exceed 7,000 times per year."* That is **19 writes
per day per point**. It drives a requirement, not a footnote — see §4.6.

### 1.3 Prior art

| What | Verdict |
|---|---|
| **`bacpypes3`** ([PyPI](https://pypi.org/project/bacpypes3/), MIT, 0.0.106 Mar 2026) | **Use this.** asyncio-native, which is what HA wants. MIT is compatible with shipping inside a HACS integration. |
| **`BAC0`** ([PyPI](https://pypi.org/project/BAC0/), LGPL-3.0) | A friendlier wrapper *over* bacpypes3. Nice for scripting; **LGPL is a licensing question we don't need**, and it adds a layer between us and COV lifetimes. Bench scripts only. |
| **`bacnet-mcp`** ([PyPI](https://pypi.org/p/bacnet-mcp)) | FastMCP server exposing BACnet read/write as MCP tools. Not part of the product, but a useful way to drive read-only probing of a live gateway during development. |
| [magliaral/ha-bacnet-hub](https://github.com/magliaral/ha-bacnet-hub) | bacpypes3-based, bidirectional, HACS. Points the wrong way (publishes HA entities *as* BACnet objects) and is ~14 months stale. Good reference for bacpypes3-inside-HA wiring. |
| [CervezaStallone/Home-Assistant-BACnet-integration](https://github.com/CervezaStallone/Home-Assistant-BACnet-integration) | GUI-only BACnet/IP client with COV. Closest existing thing. Generic — no Daikin object model, no grouping, no bulk point control, no cards. |
| [Bepacom BACnet/IP](https://github.com/Bepacom-Raalte/Bepacom-BACnet-IP-Integration) + add-on | Mature, but architected as add-on + integration and requires its add-on. Generic BACnet, no Daikin semantics. |
| Official [HA Daikin AC](https://www.home-assistant.io/integrations/daikin/) and `daikin_onecta` | **Irrelevant here.** Those are BRP069 Wi-Fi adapters and the Onecta cloud — residential split systems. Neither knows what DIII-NET is. |
| DIII-NET / `DMS502B51` HA work | **None found.** No integration, no add-on, no MQTT bridge, no Python module. |

**Conclusion:** the BACnet transport is a solved problem we should not write
(`bacpypes3`). Everything above it — the Daikin object model, group→device
grouping, bulk point control, cards — does not exist anywhere and is the
product.

### 1.4 What we already own

This is the fourth bridge, and three-quarters of the front end is built:

- **`hvac-controller-card`** already ships Daikin faceplates — `BRC1E63`,
  `BRC2E61`, `BRC1H63K`, `BRC315D7` — with roles `hvac_mode`, `hvac_action`,
  `room_temp`, `setpoint`, `fan_speed`, `swing`, `clock`. Those are the
  actual wall controllers on a DIII-NET system, so the graphics are right
  before we start.
- **`custom:bridge-devices`** dashboard strategy already builds a dashboard
  from whatever the bridges have discovered, grouped by HA area, by calling
  each bridge's `generate_cards` service. This is the whole of "auto-add to
  the overview with the chosen card, in the right area, and update
  everywhere when the card changes" — **we implement one service and get the
  feature.**
- **Niagara** has the proven service shape to copy: `generate_card`,
  `generate_cards`, `rescan`, `learn_areas`, `apply_areas`.

## 2. Architecture

```
┌────────────────────────┐                  ┌─────────────────────────────┐
│ Daikin Interface for   │   BACnet/IP      │ Home Assistant              │
│ use in BACnet          │◄──── unicast ────│  custom_components/         │
│ (DMS502B51 / B71)      │   RPM + COV      │    daikin_dbacs             │
│                        │                  │                             │
│  DIII-NET ×4 ports     │─── D3 ──────────►│  sensor.*  binary_sensor.*  │
└───────┬────────────────┘  indoor groups   │  climate.* (Phase 2)        │
        │                                   │  devices · areas · cards    │
   ▲ also serving a BMS head-end            └─────────────────────────────┘
```

**A native integration, no add-on.** Niagara needed an add-on because oBIX
polling, trend import and a point-typing UI are too heavy for the HA event
loop. DBACS needs none of that: the object model is fixed and computable, the
point count per group is 35, and `bacpypes3` is asyncio. A single integration
keeps installation to "HACS → add → type an IP".

**Unicast only — no Who-Is broadcast required.** You give us the IP. Device
discovery is one unicast Who-Is to that address to learn the device instance
(with a manual override if it does not answer), then everything is directed
traffic. This matters twice: broadcast BACnet is what forces BBMD
configuration and breaks across VLANs, and a quiet client is a client that
cannot confuse the head-end.

**We are a BACnet device too, and must not collide.** The integration binds a
local UDP port — default `47808`, overridable — and presents its own device
instance number, default high in the range and configurable, so it cannot
clash with the gateway, the head-end, or a second HA instance. Both are
config-flow fields.

**Living alongside a head-end** (decision 4) sets three rules that run
through everything below: we never write to a shared configuration object,
we read `Priority_Array` before we ever write a value, and we treat every
gateway resource as shared and finite.

## 3. Phasing

Phase 1 is shippable on its own and is honest about being read-only. Writing
into a live building is a different class of risk and gets its own phase with
its own review.

### Phase 1 — "my air conditioning is in Home Assistant" *(the quick win)*

**Scope**

1. **Config flow:** host, local port, our device instance, gateway device
   instance (optional, auto-discovered), poll interval. The connection is
   tested live before the entry is created, and a failed Who-Is or
   ReadProperty fails the form with a readable reason.
2. **Multiple gateways:** each is its own config entry. Falls out of doing
   the config flow properly; no extra work.
3. **Discovery, designed for a full gateway** (decision 5):
   - Read the Device object's `Object_List`, paged by array index rather than
     pulling ~9,000 identifiers in one segmented read.
   - Retry on `CONFIGURATION_IN_PROGRESS` with backoff — the gateway is
     scanning D3 and the answer is "not yet", not "nothing there".
   - Decode each instance into *(AC number, member)*.
   - For every AC number that appears, probe one cheap point. `UNKNOWN_OBJECT`
     means the slot is not populated; a reachable group whose
     `CommunicationStatus` reads faulted is populated but **dead**. Both are
     recorded and skipped, and both are listed in diagnostics so a group that
     comes back later is noticed.
4. **Grouping:** one HA device per live AC number. Default name is its DIII
   address, `DBACS 2 · 1-05`, with port, line and group as device attributes.
   Identifiers are `(domain, entry_id, ac_number)` so nothing re-creates on
   rename.
5. **Entities, read-only:** `sensor` for room temperature, setpoint,
   mode-as-text, fan-speed-as-text, air direction, malfunction code;
   `binary_sensor` for run status, alarm, filter sign, thermostat,
   compressor, indoor fan, heater, communication status.
6. **Selective COV plus a slow poll** (decision 6): subscribe COV on
   **run status, alarm, malfunction code and room temperature** only, and
   poll the remaining enabled members on a long interval (default 5 minutes).
   Subscriptions are renewed before their lifetime expires, and a detected
   gateway restart — `Database_Revision` change, or a `System_Status` of
   `DOWNLOAD_IN_PROGRESS` — rebuilds every subscription, because the gateway
   does not keep them. If subscription fails, that point silently falls back
   to the poll; it never goes stale without saying so.
7. **Passive alarms** (decision 7): nothing is registered in the Notification
   Class object. Alarm and malfunction state come from the objects
   themselves.
8. **Bulk point enable/disable** — see §4.5. A Phase 1 feature, not a nicety:
   256 groups × 35 members is **8,960 points**.
9. **Diagnostics** download: what was discovered, which groups were skipped
   and why, which COV subscriptions are live, what timed out, and the sweep
   duration.

**Explicitly not in Phase 1:** any write, climate entities, event
notification registration, cards, areas, outdoor units.

**Acceptance:** on a gateway with *n* live groups, HA shows *n* devices within
one sweep of setup, and the unpopulated and dead ones are absent but listed
in diagnostics; room temperature matches the wall controller; a unit powered
off at the wall reads off; a COV change in room temperature appears within
seconds; a gateway reboot restores all subscriptions without a restart of HA;
the integration survives an HA restart with no duplicate devices; a full
sweep of the enabled set completes inside the poll interval.

### Phase 2 — two-way control and faults

Gated on a written review of the write path, because of decision 4.

- **`climate` entity per group** — `hvac_mode` from mode plus on/off,
  `hvac_action` from thermostat and compressor status,
  `current_temperature` from `RoomTemp`, `target_temperature` to
  `TempAdjust`, `fan_mode` to `AirFlowRate`, `swing_mode` to
  `AirDirection`.
- **Write path, head-end aware.** Before the first write to any object we read
  its `Priority_Array` and record what is held. We write at a configured
  priority, default **16** — the lowest, because we are a dashboard and not
  the building's control system — and we never write to a priority slot
  another client occupies. Relinquishing is an explicit action, never a side
  effect.
- **The write-rate guard of §4.6**, which ships with the first write and not
  after it.
- **Error codes surfaced properly:** `MalfunctionCode` value *and* the
  two-character code from its `Description` property, plus the plain-English
  cause where we can map it. An `event` entity per group for fault
  transitions, driven from observed state changes, so history shows *when* a
  unit faulted rather than only that it is faulted now.
- **Dangerous points stay behind a switch**, off by default, with the reason
  written on the toggle: `SystemForcedOff` (forced stop),
  `RemoteControlStart` / `…AirConModeSet` / `…TempAdjust` (locks the
  occupant's wall controller out), `ForcedThermoOFFCommand`.

### Phase 3 — naming, areas, cards, dashboard

- **Rename and area allocation** in the HA UI, surviving rediscovery.
- **`learn_areas` / `apply_areas`**, copied from Niagara: learn the rules from
  the areas already set by hand, propose, dry-run, apply, never overwrite a
  human choice.
- **Card selection per device** — a stored per-device choice of faceplate
  (`daikin-brc1e63`, `brc1h63k`, `brc2e61`, `brc315d7`, generic fan-coil
  tile), with a sensible default.
- **`daikin_dbacs.generate_cards`** returning `{device, area_id, card}` in the
  shape `custom:bridge-devices` already consumes, plus `generate_card` for a
  single device. One line added to the strategy's bridge list and the
  dashboard builds itself — **and because the dashboard is a strategy rather
  than saved YAML, changing a device's card changes it everywhere on the next
  page load.** That is the auto-update-graphics requirement, and it costs
  nothing extra.

### Phase 4 — the rest

- **Synthetic outdoor units** (decision 3): one device per refrigerant system,
  built by rolling up the indoor groups that share it — compressor running,
  fault roll-up, aggregate demand, how many indoor units are calling. The
  group→outdoor mapping is entered once, from commissioning data, and stored
  with the config entry. A system view per outdoor unit.
- **Accumulated power** (Accumulator objects) wired to the HA energy
  dashboard, where the units support it. Note COV is **not** available on
  these, so they are polled.
- **Heat Reclaim Ventilators**: members 32–35, ventilation mode and amount.
- Accumulated operation time and start/stop counts for maintenance.

## 4. Design decisions

### 4.1 Which members are on by default

Ten, giving a complete-looking unit on first setup: on/off status, alarm,
malfunction code, mode status, fan status, room temperature, setpoint, filter
sign, thermostat status, communication status. On a full gateway that is
**2,560 points** — which is why §4.5 exists.

### 4.2 Reading

`ReadPropertyMultiple`, chunked to fit the 1024-byte APDU — roughly 8–10
objects per request — batched per AC number so one group's points arrive
together and can never be half-stale. Requests are issued with bounded
concurrency so one unresponsive group cannot stall a sweep, and a per-request
timeout well inside the gateway's own `APDU_Timeout`. COV covers the four
points that want to be live; the sweep is the safety net and the source for
everything else.

### 4.3 Entity naming and ids

`unique_id` = `{entry_id}_{ac_number}_{member}`. Never derived from the name,
so rename is free. Entity names are the member's plain name
("Room temperature"), with HA's device-name prefixing doing the rest.

### 4.4 Presence and availability

Three states, kept distinct, because conflating them is how a dashboard ends
up lying:

- **Not populated** — `UNKNOWN_OBJECT`. No device is created.
- **Populated but dead** — objects exist, `CommunicationStatus` faulted. No
  device, listed in diagnostics, picked up automatically if it returns.
- **Live but unreachable** — the gateway stopped answering. Entities go
  **unavailable**, never stale. A confident reading from a dead point is the
  one failure worth designing against.

### 4.5 Bulk enable/disable — two axes

The requirement is "enable/disable points in bulk", and it must work both ways
round:

- **By member, across all groups** — "give me setpoint on everything", "I
  never want heater status". An options-flow multi-select of the 35 members,
  applied to every group on that gateway, existing and future.
- **By group** — a multi-select of discovered groups, so an unused floor is
  switched off wholesale.

Mechanically: entities outside the selection are created with
`entity_registry_enabled_default = False`, so they exist in the registry,
appear greyed on the device page, and HA's own entity list can bulk-enable
them with its checkboxes. **A disabled entity is never polled and never
subscribed** — the coordinator builds its read list from enabled entities
only, which is what makes the 8,960-point ceiling survivable.

### 4.6 Write-rate guard *(Phase 2, non-negotiable)*

Daikin's spec caps setting changes at **7,000 per year per point** — 19 a day.
An automation with a bad trigger will burn through that in an afternoon and
the failure mode is a worn-out gateway, not an error message. So:

- a minimum interval between writes to the same point (default 60 s);
- coalescing — only the last value in a burst is sent;
- a rolling 24 h counter per point, a warning in the log and an HA repair
  issue raised at 50 % of budget;
- a hard daily cap, configurable, **on** by default.

### 4.7 Development against a live gateway

Decision 8 permits read-only probing at any time: `ReadProperty`,
`ReadPropertyMultiple`, `Object_List` paging, `Priority_Array`,
`Active_COV_Subscriptions`. All non-mutating. Writes — including a single test
point — wait for an agreed window with someone watching the affected unit and
the head-end's reaction.

COV subscription is **not** read-only; it consumes a per-object recipient slot
and makes the gateway send us traffic. It is therefore treated as a mutating
operation during development and tested in the same agreed window, with
`Active_COV_Subscriptions` read first and our subscriptions explicitly
cancelled afterwards.

### 4.8 Licensing and attribution

MIT, like the other bridges. `bacpypes3` (MIT) is the only runtime
dependency. Daikin, D-BACS, DIII-NET and VRV are their marks and this project
is independent and unaffiliated — same `TRADEMARKS.md` treatment as HA-Cards.

Facts to look up rather than decisions to make. None of them block starting

   ideally who maintains it.
6. **The group → outdoor-unit mapping** for Phase 4, from commissioning data.
7. **Which `TempAdjust` limits apply** per indoor model present, for Phase 2
   setpoint clamping.

## 7. Repository hygiene

This repository is **public**. Nothing site-specific goes into it — no real
IP addresses, no gateway hostnames, no property or room names, no real DIII
addresses from a deployed system — in code, comments, tests, fixtures, README
or docs. Examples use `192.0.2.x` (RFC 5737) and generic names. Test fixtures
are synthetic object lists generated from the instance formula in §1.2, which
is exactly why having that formula matters: **a complete, realistic
256-group fixture can be generated with no site data in it at all.**
